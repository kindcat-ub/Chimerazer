# Chimerazer — архитектура

Основание: `docs/ROADMAP.md` и исследование OpenSnek, OpenRazer и Snakecharmer.

## Слои

```text
apps/            исполняемые программы: CLI (M1), функциональная панель (M3)
  │
  ▼
crates/devices   адаптеры устройств: идентификация, параметры транспорта по PID,
  │              таблица команд с источником и статусом, раскладки устройства
  ▼
crates/protocol  90-байтный Razer-репорт: кодирование, CRC, статусы, проверка ответа,
  │              разбор общих полезных нагрузок. Без I/O.
  ▼
crates/transport hidraw через sysfs (M1). Только «отправить репорт / получить репорт».
```

Зависимости идут только сверху вниз: `devices` использует трейт `FeatureIo` из `transport`, чтобы цикл «запрос → ожидание → ответ» тестировался на подделке без железа. `protocol` не знает ни про устройства, ни про транспорт. `transport` не знает про протокол. Логика устройств не попадает в приложения.

## Решения

1. **Протокол — чистые функции.** Всё, что можно проверить без железа, живёт в `protocol` и `devices` и покрыто байтовыми тестами.
2. **Устройство описывается данными, а не иерархией трейтов.** Модель — модуль в `devices` с константами: PID, транспортные параметры, таблица команд, раскладка кнопок. Новое устройство — новый модуль. Общий трейт появится только тогда, когда его потребуют два реальных устройства.
3. **Транспортные параметры задаются на каждый PID, а не на модель.** Интерфейс, transaction id и задержки у провода и свистка могут отличаться (у BlackWidow V3 Mini точно отличаются).
4. **Команда без источника и статуса не существует.** Каждая команда в коде есть в таблице `docs/protocol/<устройство>.md` с источником и статусом подтверждения, и тест проверяет, что они совпадают.
5. **Ответ устройства проверяется полностью:** размер, статус, CRC, эхо transaction id, class и cmd. Эхо аргументов (профиль, слот, LED) проверяет команда, которая их отправляла.
6. **Запись в устройство — только через цикл «прочитать → записать → прочитать → сравнить»** (M2+). Подтверждение от устройства истиной не считается.

7. **Транспорт без libudev и без C-зависимостей.** Устройства ищутся перебором `/sys/class/hidraw`: VID/PID из `uevent`, номер интерфейса из `bInterfaceNumber`, размер feature-репорта — разбором дескриптора. Номер `hidrawN` нестабилен и не используется как идентификатор. Обмен — два ioctl (`HIDIOCSFEATURE`/`HIDIOCGFEATURE`) через `libc`; это единственный `unsafe` в проекте, изолирован в `crates/transport/src/ioctl.rs` (в этом crate `unsafe_code = deny` с точечным разрешением, в остальных `forbid`).
8. **Эксклюзивный доступ.** Узел открывается под `flock`: два процесса Chimerazer не перемешают команды одного устройства. Чужие программы (OpenRazer) этим не блокируются — их наличие проверяется отдельно.
9. **Ожидание ответа.** После запроса — пауза по PID (провод 600 мкс, свисток 31 мс, по OpenRazer), затем до 7 чтений с шагом 30 мс (по OpenSnek): занятые, необработанные и чужие кадры читаются повторно, статусы отказа завершают обмен сразу. Все сырые кадры сохраняются в трассу.
10. **Устройство определяется по возможностям, а не по списку моделей.** Управляющий интерфейс — любой hidraw с вендором `0x1532` и feature-репортом на 90 байт без Report ID. Модель (`MODELS` в `devices`) ищется по PID уже после этого и даёт параметры протокола; неизвестная модель видна как «unknown model», а не пропадает. udev-правило открывает все hidraw-узлы Razer по вендору, без списка PID.

## Статусы подтверждения команд

| Статус | Значение |
|---|---|
| `OurHardware` | Проверено нами на своём экземпляре устройства. |
| `ExternalHardware` | Наблюдалось на реальном экземпляре этой модели в другом проекте (захват, валидация контрибьютора). |
| `SourceOnly` | Известно только из исходников или документации, на этой модели не наблюдалось. |

Статус команды чтения становится `OurHardware`, когда команда отработала на нашем экземпляре, а сырые 90-байтные кадры запроса и ответа сохранены в протоколе проверки.

В обычном режиме записывать в устройство разрешено только командами со статусом `OurHardware` (правило действует с M2). Статус `OurHardware` присваивается командам записи только по итогам процедуры ниже. Заранее, до эксперимента, его не ставят.

## Первичная аппаратная валидация записи

Отдельный режим для первой записи командой, у которой ещё нет статуса `OurHardware`. Обычные операции им не пользуются.

**Допуск команды:**
- статус `ExternalHardware`; команда `SourceOnly` допускается только с явного разрешения владельца проекта на эту конкретную команду;
- соответствующая команда чтения уже имеет статус `OurHardware`;
- формат аргументов записи совпадает с форматом ответа чтения: что прочитали, то и можем записать обратно.

**Порядок:**
1. Снять `dump` и сохранить сырые кадры исходного состояния.
2. **Запись того же значения.** Прочитать текущее значение, записать его без изменений, прочитать снова. Состояние не должно измениться. Это проверяет кадр записи, не меняя мышь.
3. **Изменение только в живом слое** (`storage = 0`), если команда его поддерживает: записать безопасное значение, прочитать, сравнить.
4. **Возврат:** записать исходное значение, прочитать, сравнить с шагом 1.
5. **Хранимый слой** (`storage = 1..5`) — повторить шаги 2–4 на неактивном, неназначенном банке, если он читается. Активный профиль трогать последним.
6. **Переподключение:** отключить и подключить мышь (провод и свисток отдельно), прочитать. Записать, что пережило переподключение.

**Исходное состояние (реализовано в `naga_pro::params::validate`):**
- дамп, в котором есть хотя бы одна ошибка чтения, не может быть исходным состоянием — запись блокируется;
- перед первой записью снимается свежий снимок; если он отличается от исходного дампа (без `volatile.*`) или содержит ошибки — запись блокируется;
- исход каждого шага решает повторное чтение: ошибка записи при совпавшем чтении — проход с пометкой в протоколе (Naga Pro бывает сообщает об ошибке, применив значение); подтверждённая запись с расходящимся чтением — провал;
- если хоть один кадр записи ушёл в устройство, полный снимок снимается в конце всегда, в том числе после аварийного отката; любое отличие от исходного дампа — провал, даже если сам параметр вернулся (ловит побочные эффекты).

**Остановка:** любое расхождение при чтении, неизвестный статус ответа или нарушение эха — немедленный возврат к исходному значению, и команда остаётся в прежнем статусе.

**Протокол:** `docs/validation/<устройство>/<команда>.md`. В нём экземпляр (PID, версия прошивки, без серийного номера), подключение, сырые кадры каждого шага и результат. Статус в таблице команд меняется на `OurHardware` отдельным PR со ссылкой на протокол.

**Ограничение:** onboard-профили (`05:02`, `05:03`, `05:08`) через этот режим не валидируются. Для них отдельная процедура в M5.

## Восстановление из дампа (`restore`)

Реализовано в `naga_pro::restore`, команда `chimerazer restore <DUMP> [--dry-run]`.

- Дамп с ошибками чтения отклоняется целиком. Свежий снимок устройства с ошибками — тоже.
- Если `profiles.active` или `profiles.assigned` в дампе и на устройстве различаются — отказ: смена профилей не проверена.
- Пишутся только значения из `VERIFIED_WRITES` для текущего подключения: DPI, стадии DPI, яркость и эффект логотипа и колеса (таблица в `docs/protocol/naga-pro.md`). Для эффекта проверяется команда, которую требует само значение (статический цвет `0F:02/09` или Spectrum `0F:02/06`): если она вне области, значение пропускается, а оставшееся отличие делает прогон неуспешным. Остальное помечается «пропущено» или «не восстанавливается» с причиной.
- Порядок: сначала профиль 1, потом живой слой (после записи активного профиля живой слой обычно уже совпадает и не пишется).
- Совпадающее значение не пишется. Каждая запись проверяется обратным чтением; оно же решает исход, как при валидации.
- Атомарности нет: устройство не даёт транзакций. Значения пишутся по одному, первая ошибка останавливает прогон, уже записанное остаётся. Отчёт перечисляет восстановленные, неизменные, ошибочные, непопытанные и пропущенные значения и все отличия устройства от дампа после прогона.

## Происхождение знаний и лицензии

- **OpenSnek (Apache-2.0)** — можно переносить логику и данные с сохранением атрибуции в `NOTICE`.
- **OpenRazer, Snakecharmer (GPL-2.0)** — только факты (номера команд, форматы, PID, задержки). Код не читаем построчно в процессе написания и не переводим.
- Источник фиксируется с точностью до коммита: см. `docs/protocol/SOURCES.md`.
